# 接触网方块分类与注册示例

## 1. 范围与原则

本分类以 `modules/overhead_line/resources/overhead_line/blockstates/` 当前的 26 个状态资源为清单，按已有状态属性与预期行为分为 7 类；另列线材物品。资源文件存在不等于对应 ID 已注册，下面的 `kuayue:` ID 是沿用资源名称的拟注册 ID。

除已有的 `wire` 工厂外，下文所有 `overhead_*` 工厂类型与 Java 类名均为建议设计，尚未因本文自动实现。JSON 示例是内容文件中的单条声明，不是索引，也不能在没有对应工厂时直接生效。

分类依据是行为、状态和数据需求，不是外观或材料。相同朝向逻辑可以复用基类；不同模型不必拆工厂。以下分类也不是必须新增 7 个互不相关的 Java 类：能共享行为就共用或继承，只有参数不足以表达差异时才拆实现。

## 2. 分类总表

| 类别 | 数量 | 当前资源中的状态 | 建议工厂类型 | 代表例子 |
| --- | ---: | --- | --- | --- |
| A. 水平朝向构件 | 11 | facing | overhead_directional | overhead_truss_single_a |
| B. 竖向分段支柱 | 2 | vertical_type | overhead_pillar | overhead_pillar_concrete |
| C. 带朝向的分段支柱 | 2 | facing、vertical_type | overhead_directional_pillar | overhead_square_pillar_steel |
| D. 导线支撑件 | 6 | facing | overhead_support | overhead_line_support_a1 |
| E. 可壁装绝缘子 | 2 | facing、wall | overhead_insulator | overhead_line_insulator_a |
| F. 连接状态吊架 | 2 | facing、connected_type、connection_direction | overhead_hanger | truss_hanger_single |
| G. 终端配重件 | 1 | facing | overhead_end_weight | overhead_line_end_weight |
| 独立线材物品 | 不计入上述 26 个方块 | 无方块状态 | wire | overhead_line_wire |

D、G 当前状态看似与 A 相同，但可能需要连接数据、调整或专用渲染行为，因此先作为功能类别单列。如果最终只是静态展示，可以合并使用 A 的实现，不必为了分类强行新增工厂。是否需要 BlockEntity 要由实际持久化数据和交互需求决定，不能只从名称或模型推断。

## 3. 各类清单与示例

以下所有方块名称均省略 `kuayue:` 前缀。

### A. 水平朝向构件（11 个）

完整清单：

- overhead_pillar_concrete_truss_a
- overhead_pillar_concrete_truss_b
- overhead_triangle_truss_steel
- overhead_triangle_truss_steel_ad
- overhead_truss_concrete
- overhead_truss_double
- overhead_truss_double_ad
- overhead_truss_single_a
- overhead_truss_single_ad
- overhead_truss_single_b
- overhead_truss_single_c

建议行为：四向放置、旋转、镜像和对应碰撞箱。先用 `OverheadDirectionalBlock` 复用朝向逻辑；没有额外数据需求时不必添加 BlockEntity。碰撞形状不同可通过工厂参数或形状配置区分，参数必须有 Java 解析实现。

代表声明（放在内容 JSON 的 `blocks` 数组）：

```json
{
  "id": "kuayue:overhead_truss_single_a",
  "type": "overhead_directional",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

Java 必须声明水平 `facing` 状态、设置默认状态，并实现放置和旋转逻辑。现有资源的不同构件使用不同模型旋转角度，不应不加检查地统一所有模型朝向。

### B. 竖向分段支柱（2 个）

完整清单：

- overhead_pillar_concrete
- overhead_pillar_steel

建议行为：`OverheadPillarBlock` 根据上下相邻构件更新 `vertical_type`，至少覆盖现有的 `single`、`bottom`、`middle`、`top`。需要定义哪些相邻方块视为同类，放置和拆除后都要更新；不应仅注册属性而不实现状态变化。

代表声明：

```json
{
  "id": "kuayue:overhead_pillar_concrete",
  "type": "overhead_pillar",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

材料和模型不同不必拆工厂。`vertical_type` 是 Java 方块状态，不是随意加到 JSON `properties` 就能自动产生的字段。

### C. 带朝向的分段支柱（2 个）

完整清单：

- overhead_square_pillar_concrete_punching
- overhead_square_pillar_steel

建议行为：`OverheadDirectionalPillarBlock` 组合水平朝向与竖向分段更新逻辑；需明确不同朝向的相邻支柱是否可以连接。

代表声明：

```json
{
  "id": "kuayue:overhead_square_pillar_steel",
  "type": "overhead_directional_pillar",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

不要直接复用仅有 `facing` 的普通构件而保留原 blockstate：现有资源同时要求 `facing` 和 `vertical_type`。

### D. 导线支撑件（6 个）

完整清单：

- overhead_line_support_a1
- overhead_line_support_a2
- overhead_line_support_b
- overhead_line_support_b2
- overhead_line_support_c
- overhead_line_support_c2

建议行为：先由 `OverheadLineSupportBlock` 实现水平放置和可见模型，后续再接连接点、偏移调整和持久化数据。同一行为下 A/B/C 的差异优先用配置表达，但连接点参数的格式应先设计并由 Java 读取。

代表声明：

```json
{
  "id": "kuayue:overhead_line_support_a1",
  "type": "overhead_support",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

当前这类 blockstate 的模型引用是 `minecraft:air`。若没有另外接入专用渲染，注册成功也看不见。第一阶段应让它指向真实可加载模型，或明确接入客户端渲染路径。当前支撑方块实体源码中的注释代码不能算已经可用。

### E. 可壁装绝缘子（2 个）

完整清单：

- overhead_line_insulator_a
- overhead_line_insulator_b

建议行为：`OverheadInsulatorBlock` 提供水平 `facing` 与布尔 `wall` 状态，根据放置面确定安装方式，并提供相应碰撞形状。若以后承担导线连接点，再复用支撑的连接行为。

代表声明：

```json
{
  "id": "kuayue:overhead_line_insulator_a",
  "type": "overhead_insulator",
  "properties": {
    "strength": [1.0, 2.0],
    "no_occlusion": true
  }
}
```

当前状态资源要求 `wall=false/true`，且模型指向空气；不能仅登记一个普通 Block 并期待两种安装方式和模型自动生效。

### F. 连接状态吊架（2 个）

完整清单：

- truss_hanger_single
- truss_hanger_double

建议行为：`OverheadHangerBlock` 提供 `facing`、`connected_type`、`connection_direction`，根据邻接关系或交互更新状态。应逐一核对现有 blockstate 的完整取值组合，不能只凭示例补两个枚举值。

代表声明：

```json
{
  "id": "kuayue:truss_hanger_single",
  "type": "overhead_hanger",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

单、双吊架若只在模型与配置上不同，可以共享工厂；如果连接算法不同，再增加明确的配置或拆行为。复杂状态不意味着必然需要 BlockEntity。

### G. 终端配重件（1 个）

完整清单：

- overhead_line_end_weight

建议行为：第一阶段只提供朝向和外观，可复用水平朝向基类；如果需要挂线、偏移、空载或带载等真实功能，再确定专用状态和数据结构。名称并不能证明这些功能已实现。

代表声明（采用独立工厂的设计）：

```json
{
  "id": "kuayue:overhead_line_end_weight",
  "type": "overhead_end_weight",
  "properties": {
    "strength": [2.0, 3.0],
    "no_occlusion": true
  }
}
```

若仅静态展示，可改用 A 类的 `overhead_directional` 工厂，不必同时登记两条相同 ID 的声明。现有配重 blockstate 同样指向空气，必须单独处理可见模型链路。

### H. 线材物品（独立于方块分类）

代表声明（放在内容 JSON 的 `items` 数组，而不是 `blocks`）：

```json
{
  "id": "kuayue:overhead_line_wire",
  "type": "wire"
}
```

使用可复用的导线物品类，由 `wire` 工厂创建。后续电压、电流、长度等参数需要先在类与工厂中实现读取和使用，再写入 JSON `params`。物品注册成功不代表世界曲线渲染、两点连接或电气系统已完成。

## 4. 如何登记工厂并组织 JSON

参考 provisions 的模式，每个真正不同的行为工厂登记一次：

```text
模块 @Context + @PostConstruct
    → 工厂 register()
    → FactoryRegistry.register(方块类型, 创建 BlockReg 的函数)
    → 工厂内 withBlockItem(...) 创建配套方块物品

FactoryRegistry.registerItem("wire", 创建 ItemReg 的函数)
    → 独立线材物品
```

工厂需完成对应 `BlockReg` 泛型适配，参照 `ProvisionsFactories` 的写法；上面的流程不是可直接复制编译的 Java 代码。

内容文件可先只包含一个代表性支撑与一个线材：

```json
{
  "blocks": [
    {
      "id": "kuayue:overhead_line_support_a1",
      "type": "overhead_support",
      "properties": {
        "strength": [2.0, 3.0],
        "no_occlusion": true
      }
    }
  ],
  "items": [
    {
      "id": "kuayue:overhead_line_wire",
      "type": "wire"
    }
  ]
}
```

注意：

1. 上面的 `overhead_support` 工厂仍需实现后才能使用；强度数值仅为演示，不是已有默认值。
2. `withBlockItem(...)` 已生成配套方块物品时，不要在 `items` 再重复注册同一物品 ID。方块和配套物品在各自注册表使用同名是正常的，重复的是同一物品注册表中的两份声明。
3. JSON 管线负责挂入注册树，不要再手动用 Java 静态条目注册相同 ID。
4. 可以按类别拆成多个内容文件，但每个都要列入 data-driven 索引 `on_register`；内容文件不要误放进索引目录。
5. 创造模式标签页必须引用实际已经注册的 tab；示例暂不指定 tab。

## 5. 模型和资源入口

源资源根目录：`modules/overhead_line/resources/overhead_line/`。

```text
module.toml                                  空的资源模块标记
 data/kuayue/kasuga_lib/data_driven/overhead_line.json
                                             索引：列出内容文件
 data/kuayue/kasugalib/overhead_line.json       内容：blocks、items 等
 blockstates/<方块名>.json                    状态到模型映射
 models/block/...                            方块模型与必要几何资源
 models/item/<物品名>.json                    背包物品模型
 textures/...                                对应贴图
```

- 普通物品可以继续使用 `item/generated`，无需强行加特殊 loader。
- 特殊模型使用与文件格式匹配的 KasugaLibNext 加载器；例如现有绝缘子模型使用 `kasuga_lib:bedrock_animated`，还需配齐对应几何文件、标识符和贴图。
- Java 声明的状态属性、默认值、取值范围必须匹配 blockstate。不能用无状态普通方块直接承接所有旧状态文件。
- 支撑、绝缘子、配重目前的空气模型引用不能作为可见模型验收通过的证据。
- 不编辑 `modules/overhead_line/src/compiled/resources/` 或 `build/` 中的生成产物。

## 6. 推荐落地顺序与验收

1. 完成 D 类中的 `overhead_line_support_a1`、独立线材和一个真实可见支撑模型，符合“先一个代表样例”的需求。
2. 验证两个 ID 可获取、支撑可放置和破坏、世界与背包模型正常。需要掉落时再补配套掉落资源并验证，不把“可破坏”等同于“已有正确掉落”。
3. D 类行为验证通过后，才扩展同类其余 5 个 ID。
4. 实现 A 类并扩展朝向构件，再处理 B/C 分段支柱、E 绝缘子、F 吊架、G 特殊配重；顺序可根据依赖调整。
5. 后续才接复杂连接、可调参数、网络同步和电气逻辑，最后验证专用服务端兼容性。

最低检查项：

- 无找不到工厂、索引源文件缺失、重复注册错误。
- `/give @s kuayue:overhead_line_support_a1` 与 `/give @s kuayue:overhead_line_wire` 成功。
- 朝向、分段、壁装、连接状态分别按所属类别测试。
- 模型不为空气或紫黑缺失材质，碰撞范围合理。
- 同类新增 ID 不需要重复编写一份 Java 行为类。

本文仅提供分类和迁移方案，不代表这些方块已实现或已通过构建、运行验证。
