### 1. 原色25T车厢密封窗户（金属框 / 蓝色框）黑紫块 —— 已修复
- 方块：`kuayue:window_oc_wide_sealed_25t`、`kuayue:window_oc_wide_sealed_blue_25t`
- 根因：blocks.json 用了 `train_unopenable_small_window`，该类型（`TrainUnOpenableSmallWindowBlock`）
  只有 FACING + EDIT_STATE，**没有 hinge 属性**；但 blockstate 的 variant key 是 `facing=...,hinge=left/right`。
  Minecraft 无法为不存在的属性匹配 variant → 选不中模型 → 显示原版"缺失模型"紫黑格。
- 修复：改为 `train_unopenable_window` + `params {"wide": 2}`，与正常工作的兄弟方块
  c25b `window_oc_wide_sealed_25b` / c25k `window_oc_wide_sealed_25k` 完全一致。
- 通用规律：**数据驱动方块的 blockstate variant key 里出现的属性，方块类型必须真的拥有**。
  工厂类型 → 状态属性的对应表在 `modules/train-parts/.../factory/BlockFactories.java` 与各 Block 类的
  `createBlockStateDefinition` 里。

### 2. M1 客车端面 / M1 客车内侧端面 模型错位 —— 已修复
- `kuayue:end_face_m1`（外侧端面，type=`meter_carriage_end_face`, door_type=no_door, outside=true）
  - 根因 A（唯一的真实错位）：`RenderShape.MODEL` 会渲染 blockstate 模型（`m1_end_face` OBJ），
    同时方块实体渲染器**又**渲染了一份 frame —— 而 `MeterCarriageEndFaceBlock` 的三参构造器把
    frame 硬编码成了"内侧端面"的 `m1_middle_end_face_frame`，两者位置差 1 格 → 出现鬼影。
  - 修复：
    - `CustomRenderedEndFaceBlock`：frameModel 允许为 null（原来直接 `PartialModel.of(null)` 会 NPE）。
    - `MeterCarriageEndFaceBlock` 三参构造器改传 null frame → 外侧端面只画 blockstate 模型。
  - 复核结论：**blockstate 的 y 旋转本来就是对的**，无需改动。
    `m1_end_face` OBJ 的平板在北侧（z -0.494..0.062），而碰撞盒用 `getEndFaceShape(facing.getOpposite())`，
    两者靠 blockstate 的 y 旋转互补：north=180 / south=0 / east=270 / west=90，
    实测四个朝向模型与碰撞盒都精确吻合（这是 block-model 路径，没有渲染器的 ±1 格 Y 补偿）。
- `kuayue:end_face_middle_m1`（内侧端面，door_type=slide）
  - 根因：框/门模型都是按"碰撞盒坐标系"建的（元素坐标即碰撞盒坐标），
    但方块实体渲染器对**框**额外做了 `T(0.5,-1,0.5)·R·T(-0.5,2,-0.5)`，净效果是**框整体 +1 格 Y**
    （与朝向无关）；而**门**的净 Y 偏移是 0（`T(0,1,0)` 抵消了外层 -1）。
    → 框比碰撞盒高 1 格，而门正好对齐 —— 框与门互相错开 1 格。
  - ⚠️ 踩过的坑：**不能靠下移框模型来修**。Minecraft 硬性限制方块模型元素坐标在 **[-16, 32]**，
    框高 40 单位（y -8..32），下移 16 后 y=-24 越界 →
    `JsonParseException: 'from' specifier exceeds the allowed boundaries` → 模型加载失败 → 紫黑块。
    （全包 497 个方块元素模型都在 [-16,32] 内，说明这确实是硬约束。）
  - 正确修法：**在渲染器侧抵消这 1 格**，而不是动模型。
    - `CustomRenderedEndFaceBlock`：新增 `frameOffsetY` 字段（默认 0）+ 一个带该参数的重载构造器。
    - `CustomRenderedEndFaceEntity`：新增 `getFrameOffsetY()`（与 `getFrameModel()` 同款取法）。
    - `CustomRenderedEndFaceRenderer`：`pose.translate(-.5, 2 + frameOffsetY, -.5)`。
    - `MeterCarriageEndFaceBlock`：本家族 `FRAME_OFFSET_Y = -1`（因为 M1 端面用原生元素模型建模）。
    - OBJ 端面（25T / c22 / cr200j）frameOffsetY 保持 0 → 行为完全不变。
  - 门的三次尝试（均为**数据侧**改动，不碰共享渲染逻辑）：
    1. 门元素 Z −16 → 门扇渲染后落在框厚内部（z 0.844..0.906），与框表面齐平但嵌进墙里，不对。
    2. 回退位移补偿、改用 X +1.6 / Z −14（扣掉渲染器位移，让门扇精确落在作者设计位置
       x 0..16 / y −7..25 / z 15.5..16.5）→ 门扇平贴在墙上，与作者的 Blockbench 模型一致，
       但**游戏里看起来不对**（用户截图：门扇和墙的观感不对，正确的观感应是竖起来插在开口里）。
    3. **最终采用：回退位移补偿 + 绕 Y 轴反向旋转 90° + 位置微调**，门扇变成插销门（薄在 X、延伸在 Z）：
       变换 `new_x = old_z - 6.4`、`new_z = 8 - old_x`（行列式 +1，UV 附着关系不变，不镜像贴图），
       面朝向映射 north→west / west→south / south→east / east→north。
       - `-6.4` = 把薄轴对到开口中心（渲染器对门有固定 X 位移 −1.6 单位，要补掉）
       - `8` = 深度以墙板(z=13..15 单位)为中线，使门扇**穿过墙板**、两侧各露约 0.44 格
         （一开始让门扇整格飘在墙体外侧 1 格，实机看像根独立柱子，不像墙上的门）
       渲染后：X 0.469..0.531 格（= 开口中心）、Y −0.438..1.562 格（= 开口高度）、
       Z 0.375..1.375 格（穿过墙板 0.812..0.938，两侧各 0.438 格）。
  - ⚠️ 方向的关键几何依据：**M1 内侧端面的墙板位于方块的南侧（z 13..15 单位），
    通道/车厢内侧在北侧（z < 13）**，所以插销门必须朝北插入。

  - 框的 X/Z、门的 Y 未改：它们本来就与碰撞盒的 x/z、开口 y 精确对应
    （门的 y=−7..25 与框的开口 y 完全吻合）。
  - 复核（模拟渲染变换，facing=north）：框 X/Z 与碰撞盒**逐位一致**，框 Y 底边一致；
    门扇薄轴落在框开口内、Y 与开口吻合、深度 1 格穿过门框平面。

## 项目约定备忘（端面模型坐标系）
- **方块模型元素坐标硬约束**：`from`/`to` 的每个分量必须落在 **[-16, 32]**，否则模型加载失败
  → 表现为原版"缺失模型"紫黑格。端面模型高 2~2.5 格时，下移整格几乎必然越界，
  优先考虑在渲染器/方块侧做偏移，而不是改元素坐标。
- 方块模型坐标：元素 from/to 以 1/16 格为单位，**相对于方块角**（不是中心）。
  X/Z 超出 [0,16] 合法（端面会跨格）。
- `neoforge:obj` loader：顶点原样使用，1 单位 = 1 格，同样以方块角为原点。
- 端面渲染器 `CustomRenderedEndFaceRenderer` 的固定位移表（单位：1/16 格）：
  | 对象 | 净位移 | 说明 |
  |---|---|---|
  | frame | X 0、**Y +16**、Z 0 | 恒定 +1 格 Y；OBJ 端面的框因此要建低 1 格 |
  | door  | **X −1.6**、Y 0、**Z +14** | 缓冲 translate(−0.6,0,+0.375) + 姿态 T(0.5,−1,0.5)·T(0,1,0) |
  - ⇒ **建模约定：端面模型按"作者设计位置"建（= 渲染后应到的位置）时，必须自行扣掉上表位移。**
    门的 X/Z 偏移就是最容易漏的一项，漏了门扇会偏离框的开口。
  - `frameOffsetY`（本次新增，默认 0）：给用**原生方块元素模型**建模的端面家族（M1）用 −1 抵消 frame 的 +1 格。
- `Direction.toYRot()`（1.21.1，data2d = 枚举序号 DOWN/UP/NORTH/SOUTH/WEST/EAST）：
  **NORTH=180, SOUTH=270, WEST=0, EAST=90**（实体 yaw 约定，已用字节码核实）。
  注意与 MC 方块状态 `"y":θ` 不同：方块状态的 y 是绕 +Y 旋转 -θ。
- 排查端面问题最快的手段：看 `modules/train-parts/run/logs/latest.log` 里的
  `Failed to load model ...` 与 `JsonParseException`（模型越界/加载器缺失都在这里报）。
- M1 内侧端面的美术基准：作者的 Blockbench 模型里，端面墙是 3 块隔板、中间面板带窗；
  门扇元素模型 `m1_middle_end_face_door` 单独建，宽度正好 1 格（= 框开口宽度），厚度 1 单位。
  **游戏里的正确观感是门扇竖起来插在开口里（垂直于门框），不是平贴**（用户实机截图确认）。



### ⚠️ 已发现的既有不一致（本次未改动，供后续排查）
`CustomRenderedEndFaceRenderer` 用 `R = rotY(-toYRot(facing.getOpposite()))`，
而 `EndFaceBlock/MeterCarriageEndFaceBlock.getShape` 用
`EndFaceShapes.getEndFaceShape(facing.getOpposite(), ...)`。
两者叠加后只有 `facing=south` 方向自洽；north/east/west 会互相差 90°，
表现为端面模型与碰撞盒的平板侧别对不上（25T / c22 / cr200j 也同样受影响）。
即"端面朝向"在项目里存在系统性方向约定冲突，若要彻底修好需要统一
"facing 指向车厢内侧还是外侧"的定义 —— 属于跨模块改动，未纳入 Issue #24 范围。
本次只做了"不动方向、只对齐模型坐标"的最小修正。
